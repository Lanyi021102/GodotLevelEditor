# 更新 Wiki

功能修改完成时，同步修改用户会查阅的页面和模块接口。网站由项目内 Markdown 生成，网页没有另一份独立正文。

## 从哪一页改起

| 功能变化 | 同步页面 |
|---|---|
| 新增或调整入口 | [功能地图](../features.md)，必要时更新 [快速开始](../getting-started.md) |
| 调整轮盘、放置或选择方式 | [关卡操作](../guides/levels.md)、[快捷键](../reference/glossary.md) |
| 新增机关、状态、动作或端口 | [机关速查](../reference/mechanisms.md)、相关案例与模块 INTERFACES |
| 改变任务接取或对象生命周期 | [功能地图](../features.md)、[常见问题](../faq.md)，及套件 / 关卡接口 |
| 调整文件位置、格式或检查命令 | [维护索引](index.md) 与对应模块接口 |
| 删除或替代旧功能 | 当前指南、搜索内容和历史入口提示；保留可追溯记录 |

## 每次更新的顺序

1. 阅读任务相关的 README 与 INTERFACES，核对实际代码和界面文字。
2. 修改唯一来源页面；其他页面优先链接到它，避免复制长篇参数说明。
3. 操作顺序变化时，补齐前提、具体步骤、预期结果和失败排查。
4. 涉及界面变化时更新真实截图；不要把旧截图标为当前实测。
5. 在 [版本记录](../changelog.md) 说明用户可见变化，在模块验证记录填写实际检查结果。
6. 构建 Wiki 并检查链接与搜索；涉及游戏功能时再运行相应 Godot 检查。

## 新教程的写法

页面标题使用具体目标，例如“让 NPC 在对话后交给玩家任务”。正文按下面的顺序组织：

```text
# 要完成的目标
准备：需要的场景、素材、数据和版本
预期结果：完成后会看到什么
1. 打开具体入口
2. 修改具体参数
3. 保存并试玩
完成检查：可观察、可复现的结果
常见失败：症状、原因和处理入口
维护依据：接口、代码位置和验证记录
```

每个教程都应能在副本或新资源上完成。需要改内置素材时先说明“另存为”，示例资源不自动写进用户工作簿或默认入口。

## 新增页面与截图

- 当前指南放在 `docs/wiki/`，首页在 `docs/index.md`。
- 用小写英文文件名形成稳定网址；标题和内容使用中文。
- 在 `mkdocs.yml` 的 `nav` 中添加导航项，否则它不会出现在目录里。
- 截图可引用已有专项路径，保持一份源图；新的 Wiki 专用图放入 `docs/wiki/assets/`。
- 链接使用相对路径，锚点需要稳定时显式声明，例如 `{#task-start}`。
- 网站生成目录 `site/` 与 `.venv-wiki/` 已忽略，不提交为工程源文件。

## 搜索与历史资料

搜索收录首页与 `docs/wiki/` 的当前说明。`tools/wiki/hooks.py` 为原有专项页面添加提示，并将其排除出主搜索；原文件与链接仍保留。

历史页面可能引用未入库日志或旧路径。未随站点提供的附件显示为文字；旧锚点问题保留信息提示。`tools/wiki/check.py` 会独立检查 Wiki 当前页面的本地链接、锚点、截图与搜索范围，当前指南的坏链接仍会导致检查失败。

## 给后续协作者的约定

工程根 `AGENTS.md` 已登记 Wiki 的维护入口。功能更新时，协作者需要记录改了哪些用户说明、哪些接口，以及实际做过什么验证。文档里的“已验证”必须来自本次实际检查或明确标注日期的既有验证记录。
